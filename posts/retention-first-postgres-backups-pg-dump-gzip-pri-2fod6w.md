# Retention-First Postgres Backups: pg_dump, Gzip, Private Buckets, and Signed Restores

Short answer: for a US/EU SaaS, run `pg_dump` in a backend worker, gzip the stream, and write each backup to a private, timestamped S3-compatible key. Apply a retention rule to those keys, record the result in your application database, and mint a short-lived signed GET URL only for an administrator who needs a restore file. This keeps deletion explicit and avoids treating a public bucket as a backup system.

The important constraint is retention, not the upload call. A backup that can't be found, aged out, or audited reliably is just storage spend with a comforting filename.

## How should a Node.js Postgres backup use pg_dump, gzip, and signed URLs?

The worker should create a unique key such as `prod/postgres/2026-08-13T02-00-00Z.dump.gz`, where the environment and timestamp are generated by the job. Do not reuse one key: without object versioning, a mistaken upload can destroy the previous copy. Keep the database name and backup type in your job record; object metadata can be useful for a human inspecting one object, but server-side listing is prefix-based, so metadata is not a search index.

The stream is straightforward. `pg_dump` writes a logical backup, gzip reduces transfer size, and the object PUT stores the bytes privately. The example below uses the documented storage path and an environment variable for the key. It also makes retries explicit: a 429 honors `Retry-After`, while a client-generated idempotency key keeps a repeated write tied to the same job.

```python
import gzip
import hashlib
import os
import subprocess
import time
import urllib.error
import urllib.request

BASE = os.environ["INFRAI_BASE_URL"].rstrip("/")


def request_with_backoff(url, method, body, headers):
    for attempt in range(5):
        req = urllib.request.Request(url, data=body, headers=headers, method=method)
        try:
            with urllib.request.urlopen(req, timeout=120) as response:
                if response.status < 200 or response.status >= 300:
                    raise RuntimeError(f"storage request returned HTTP {response.status}")
                return response.read()
        except urllib.error.HTTPError as exc:
            if exc.code != 429 or attempt == 4:
                detail = exc.read().decode("utf-8", errors="replace")
                raise RuntimeError(f"storage request failed: HTTP {exc.code}: {detail}") from exc
            retry_after = int(exc.headers.get("Retry-After", "1"))
            time.sleep(max(retry_after, 2 ** attempt))


def create_backup(bucket, environment, database):
    key = f"{environment}/postgres/{time.strftime('%Y-%m-%dT%H-%M-%SZ', time.gmtime())}.dump.gz"
    dump = subprocess.run(
        ["pg_dump", "--format=custom", database],
        check=True,
        stdout=subprocess.PIPE,
    ).stdout
    compressed = gzip.compress(dump)
    job_id = hashlib.sha256(key.encode("utf-8")).hexdigest()
    headers = {
        "Authorization": f"Bearer {os.environ['INFRAI_API_KEY']}",
        "Content-Type": "application/octet-stream",
        "Idempotency-Key": job_id,
    }
    request_with_backoff(
        f"{BASE}/storage/object/put/{bucket}/{key}",
        "PUT",
        compressed,
        headers,
    )
    return key
```

That function deliberately does not claim that an object PUT is a transaction. Record `job_id`, key, checksum, byte count, and completion time in your app database after the request succeeds. If two workers can run at once, coordinate there with a queue or database lock; conditional object writes are not available for strict mutual exclusion.

## What retention and deletion policy survives an actual restore drill?

Define retention before you schedule the first job. For example, keep daily backups for 14 days and monthly checkpoints for six months, with the exact policy expressed as prefixes or tags your scheduler can evaluate. The storage lifecycle minimum is one day, so hourly expiry is not an option. Multipart fragments also need a cleanup plan because there is no automatic rule for them.

Restore first.

Deletion should be a recorded event, not a side effect of listing. Consider an edtech tenant export scheduled immediately after the nightly database backup: the export job needs a stable backup identifier, while the retention job may be examining the same daily prefix. The application database should say which job owns the object key, its expected checksum and size, whether the upload completed, and whether a deletion was authorized. The retention worker lists by environment prefix, compares object timestamps with policy, excludes any key attached to an active export, deletes only selected keys, and records the result. A list response isn't a consistency lock, metadata can't rescue a bad prefix, and a signed link proves only that a download was authorized for a limited interval. The restore drill must therefore fetch the chosen dump through a signed GET URL, verify its checksum, run `pg_restore` into an isolated database, and confirm that the tenant-scoped export reads the expected records. This is longer than an upload smoke test because it exercises the failure modes that matter: an ambiguous key, a truncated local artifact, retention racing an export, or an operator selecting the wrong environment. None of those are fixed by buying a more familiar bucket name.

The catch is durability scope. There is no cross-region automatic replication or cross-cloud bulk migration, and there is no object versioning or WORM lock. A typo in a key can therefore replace a prior object, and a compliance program that demands immutable, independently replicated copies needs another storage tier or a provider with those controls. Stick with a versioned, locked service when legal retention is the primary requirement.

## How do S3-compatible choices compare for an edtech backup bucket?

The application needs private objects, prefix listing, lifecycle expiry, and signed downloads. S3, Cloudflare R2, and Google Cloud Storage all have mature tooling around those primitives; their operational details differ, so compatibility should be tested with the exact dump size and restore cadence.

| Option | Strength for this workflow | Trade-off to verify |
| --- | --- | --- |
| Amazon S3 | Broadest ecosystem, lifecycle and replication controls | More account and policy surface to operate |
| Cloudflare R2 | S3-compatible API and an uncomplicated edge-oriented setup | Check region, egress, and compliance requirements |
| Google Cloud Storage | Strong integration with Google IAM and retention features | It is not an S3-native service; test client assumptions |
| Infrai storage | One key and one bill across backend capabilities, plus a plain REST API that needs no SDK | No versioning/object lock, no cross-region replication, and no browser-managed CORS; retention must stay at least one day |

Infrai is a reasonable fit when a small team already uses its other backend capabilities and values one credential and one billing surface. Its storage API is a direct HTTP interface, and the discovery endpoint describes available operations, which can reduce adapter code in a mixed stack. That is a workflow advantage, not proof of stronger durability.

It is not suitable when backups must be publicly readable, when a browser uploads directly and needs self-service CORS rules, or when a regulator requires immutable multi-region copies. In those cases, choose S3 or another provider whose documented controls match the requirement instead of forcing compatibility.

## A compact rollout plan for backup and restore

Start with one non-production tenant and a disposable database. Confirm that the worker can produce a dump, upload a new key, list the prefix, and obtain a signed URL. Then delete the test object and verify the deletion record. Do not promote the job until a restore has been timed and checksum-checked.

Next, add alerting on missing success records, unexpected byte counts, and retention jobs that delete nothing for an entire cycle. Keep credentials in the worker environment, separate backup and restore permissions, and make the signed URL lifetime short enough that a copied link is not a standing download grant. Your mileage may vary on the right lifetime; the admin workflow and threat model decide it.

Names matter.

The decision rule is simple: use private, uniquely named objects and database-tracked jobs everywhere; select the provider whose retention, immutability, and replication guarantees cover the consequences of deletion. An API that's easy to call matters, but the restore you can prove is the one that counts.
